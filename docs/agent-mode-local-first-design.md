# Развитие агентного режима: local-first, VLM-first

Дата исследования: 2026-09-21. Статус: предложение, не реализованный контракт.

## 1. Решение в одном абзаце

Развивать не «более длинный system prompt», а общий управляемый агентный цикл для Desktop и VS Code: модель выбирает следующий шаг, приложение проверяет аргументы и полномочия, выполняет инструменты, сохраняет доказательства и собирает следующий ограниченный контекст. Локальная модель — основной исполнитель; облако — явно разрешённая альтернатива. Сначала исправить транспорт изображений и протокол инструментов, измерить цикл и контролировать контекст каждого шага. Затем переиспользовать KV-префикс и развивать адресную память, навыки и обнаружение инструментов. Мультиагентность и несколько одновременно загруженных LLM не являются первым этапом.

## 3. Как сейчас устроено

### Runtime

Go host/worker обслуживает инференс через llama.cpp, загрузку и подбор параметров памяти. Есть native chat-template/tool API, отделение reasoning, типизированные ошибки и ограниченные повторные попытки загрузки. Исполнение инструментов и память задачи находятся не здесь.

`internal/service/scheduler.go:38` задаёт один inference slot. `internal/engine/completion.go:204,374` очищает KV-кэш перед обычным и потоковым completion. При наличии tools `completion.go:411–462` не выдаёт частично разобранные content/reasoning: результат разбирается после генерации. Это важно для восприятия задержки агентных шагов.

### VS Code

Есть полезная основа: `AgentRunState`, проверка повторов/остановки, permissions, артефакты изменений, verify/repair, replay-тесты, retrieval с текстовым поиском и опциональными embeddings. `openAiCompat.ts` компилирует контекст под окно и сохраняет группы вызовов/результатов инструментов. Это следует переиспользовать.

Однако координация провайдеров и агентных веток остаётся в `src/OrchestraPanel.ts` (~9 тысяч строк). Выбор tools во многом зависит от regex по исходному запросу. `skillStore.ts` выбирает до двух навыков и обрезает каждый до 6000 символов. Каталог progressive disclosure существует, но его наличие само по себе не доказывает доступность всех discovery-возможностей в каждом provider path.

### Desktop

`use-chat.js` собирает историю и запускает предварительную compaction. `runtimeClient.js` содержит отдельные OpenAI-совместимый и Ollama tool loops, по умолчанию до 24 раундов. MCP-процессы уже переиспользуются через общую сессию — запускать отдельный сервер на каждый ход не требуется.

Есть ограничение schemas по токеновой оценке, чтение skills по требованию, журнал выполнений и разрабатываемая пользовательская память. Но большая часть общения между runtime loop и UI передаётся текстовыми маркерами `<think>`, `<operium-exec>`, `<operium-usage>`.

| Desktop `flattenToolResult` преобразует нетекстовые MCP blocks в JSON-строки | Изображения теряют модальность; base64 рискует попасть в текстовый бюджет; structured results не сохраняют отдельный контракт | P0/P1: нормализатор текстовых, structured, image и resource результатов |
| VS Code обрезает активный skill посимвольно и читает `.orchestra/skills`; Desktop использует `.agents/skills` | Разные навыки и поведение между клиентами; у обрезанного skill могут исчезнуть проверки или запреты | P1: единый resolver, полная загрузка обязательной инструкции, совместимость путей |
| Desktop memory выбирает темы по новизне, хранит account-level заметки в localStorage и вставляет в system context | Нет полноценной адресной проектной памяти, provenance и контроля устаревания | P1: scoped, source-backed memory; не назначать всем сохранённым фактам авторитет инструкций |
| Desktop `contextFit.js` использует единую константу KV bytes/token; runtime имеет собственный planner | Два разных источника решения о доступном контексте | P1: runtime сообщает фактический профиль и оценку; клиент не воспроизводит арифметику загрузки |

Это подтверждённые особенности показанных путей, а не утверждение, что все модели или все provider paths воспроизводят одинаковую ошибку. Перед исправлением каждому P0 нужен отдельный регрессионный сценарий.

## 5. Целевая архитектура

```text
Desktop UI / VS Code UI
           │ команды пользователя, typed events
           ▼
Общий Agent Core — библиотека без зависимости от UI
  state machine · context compiler · budgets · completion checks
       │                │                    │
       ▼                ▼                    ▼
 Provider adapters   Memory/artifact store   Tool broker + policy
       │                                     │
       ├─ Orchestra Runtime                  ├─ builtin tools
       ├─ Ollama / LM Studio                 ├─ MCP plugins
       └─ cloud model API                    └─ skill scripts

Native host (Tauri / VS Code host): процессы, файлы, секреты, sandbox
Orchestra Runtime: модели, templates, tokens, KV, memory admission
```

Начать с общей TypeScript-библиотеки контрактов и чистых функций: оба клиента уже используют JS/TS. Не переносить Go inference в TS и не переносить shell/MCP secrets в WebView. Библиотека может работать с Tauri через узкие IPC-интерфейсы; решения о правах обязательно повторно проверяет доверенный host. Вынос целого agent runner в отдельный процесс — последующая задача, если нужны независимые от окна фоновые запуски.

Отделить обычный model provider от **hosted agent provider**. Codex app-server уже владеет своим tool loop и серверной историей. Для него нужен adapter событий/сессии, а не второй локальный цикл поверх него. Нельзя заявлять одинаковый контроль контекста для plain inference API и hosted agent API.

Минимальный общий протокол: `run_started`, `phase_changed`, `content_delta`, `reasoning_delta`, `tool_call_ready`, `tool_started`, `tool_finished`, `usage`, `checkpoint`, `run_finished`. У каждого события есть `runId`, `stepId`, монотонный `sequence`. UI строит представление из событий, а не парсит HTML-подобные маркеры внутри ответа модели. Пользовательский текст, содержащий такие маркеры, не должен создавать фиктивное выполнение инструмента.

Нормализованные исходы: completed, needs_input, budget_exhausted, cancelled, provider_error, tool_protocol_error, verification_failed. Отсутствие tool calls ещё не доказательство успешного выполнения задачи.

## 6. Эффективный цикл для локальной модели

1. Зафиксировать цель, scope, режим доступа, критерий результата, профиль модели и общий бюджет.
2. Определить прямой ответ или tool workflow. Не требовать план, TODO или отдельную LLM-классификацию для каждого простого вопроса.
3. Собрать контекст и небольшой набор релевантных tools; проверить вместимость.
4. Получить typed stream. Дождаться полного вызова; проверить имя, JSON, schema, scope, разрешение.
5. Выполнить шаг с deadline; сохранить исходный результат и компактное представление для модели.
6. Обновить проверенное состояние силами host; при необходимости перестроить контекст.
7. Завершить по критерию задачи или продолжить. При исчерпании бюджета выдать честный checkpoint, а не повторить тот же запрос.

Ограничивать не только число итераций: учитывать время, суммарные input/output tokens, schema tokens, число ошибочных вызовов, повторов и платных операций. Максимум шагов остаётся аварийным ограничителем, не целевой длиной работы.

Повтор с теми же аргументами блокируется только с учётом изменения состояния: повторное чтение после edit и повторный тест после fix нормальны. Fingerprint включает инструмент, канонические аргументы и версию ресурса. Повторная сеть допустима для явно transient ошибок и безопасной операции, с ограничением попыток и backoff. Неизвестный результат записи после timeout — состояние `unknown`, а не повод автоматически повторять mutation.

Начальный режим небольшой локальной модели: один простой вызов за шаг. Независимые чтения можно объединить в host-level `read_files`/`search` batch, а для моделей, прошедших eval, выполнять несколько read-only calls параллельно. Это не требует нескольких inference slots. Мутации одного ресурса последовательны; browser session и shell cwd тоже являются разделяемыми ресурсами.

Вместо требования к маленькой модели написать большой orchestration script сначала использовать узкие инструменты и готовые операции фильтрации/агрегации. Programmatic execution полезен для массовых данных, но вводится позже, в sandbox с теми же permissions, deadline и лимитом вывода. Экономия промежуточного контекста описана в [исследовании MCP code execution](https://www.anthropic.com/engineering/code-execution-with-mcp); переносить численные результаты чужих моделей на наши нельзя.

## 7. Контекст: один compiler перед каждым шагом

Инвариант:

```text
rendered_prompt_tokens + reserved_generation_tokens + safety_margin
    <= effective_context_window
```

`rendered_prompt_tokens` включает chat template, system instructions, schemas, историю tools, изображения и текущий запрос. Резерв генерации включает reasoning в рамках модели/провайдера, а не только видимый ответ. Нельзя считать изображения по длине base64 или объявлять chars/token точным счётчиком.

Добавить в runtime версионированную возможность preflight/render+token-count для того же template и фактической модели, которыми будет выполнен запрос. Сначала можно считать текст точно, а vision давать консервативной оценкой с явным признаком `estimated`; конечная admission-проверка остаётся в worker. Запрос связан с fingerprint загруженной модели/профиля: переключение модели между preflight и inference не должно делать результат «точным» для другого профиля.

Для внешних providers — их tokenizer/count API, если доступен; иначе оценка с запасом и калибровкой по usage. Не делать дополнительный удалённый count-запрос на каждый маленький шаг без оценки его latency. Кэшировать стоимость неизменных текстовых blocks.

Пример распределения окна 16 384 токена для первых экспериментов: до 12 000 входных, 3 500 на генерацию, 884 запаса. Входной бюджет делится между обязательными инструкциями, schemas, task state, свежими наблюдениями и историей. Это не жёсткие универсальные доли: reasoning- или vision-задаче может требоваться другой баланс.

При недостатке места:

1. Убрать точные дубликаты и устаревшие excerpts.
2. Отложить неиспользуемые tools и справочные skill-материалы.
3. Заменить большие завершённые tool outputs на bounded summary + artifact reference.
4. Сжать старую историю, сохранив исходный запрос, ограничения, решения и незаконченные действия.
5. Если обязательный минимум всё ещё не помещается — явно предложить меньшую задачу, другой профиль/модель или разрешённое облако.

Не вырезать safety/project rules регулярными выражениями и не разрывать assistant tool call ↔ tool result. Большое одиночное сообщение требует адресной выборки либо явного отказа, а не исключения из бюджета.

Compaction — отдельная операция с собственным бюджетом; её нельзя запускать с уже переполненным запросом. Сохранять исходный журнал. Сначала детерминированно сворачивать tool outputs и факты, LLM-summary использовать для повествовательной части. Проверять наличие цели, запретов, pending действий и точных идентификаторов. Установить hysteresis: после compaction освобождать достаточно места для нескольких шагов, а не запускать её после каждого ответа.

Подход адресной загрузки контекста вместо постоянной вставки всей истории согласуется с [context engineering Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents). Конкретный compiler и бюджеты выше — предложение для нашей архитектуры.

## 8. Пять разных видов памяти

| Вид | Что хранить | Как использовать |
| --- | --- | --- |
| Состояние задачи | Цель, запреты, pending steps, проверенные изменения, результаты тестов | Небольшой checkpoint на каждом шаге |
| История/артефакты | Полные сообщения, tool outputs, изображения, diffs | По ссылке/диапазону, не целиком в prompt |
| Долговременная память | Предпочтения, проектные решения, устойчивые факты | По scope и релевантности, с provenance |
| Индекс знаний | Код, документация, repo map, поисковые индексы | Retrieval по актуальной версии ресурса |
| KV-кэш | Вычисленное состояние префикса конкретной модели | Только ускорение; не источник истины и не хранилище знаний |

### Состояние задачи и хранение

Сохранить сильные части `AgentRunState` и Desktop execution journal, но выполнять update проверенных действий из результатов tool runner. Модель может предложить гипотезу/план, но не записать «тесты прошли» без соответствующего execution record.

Для локального persistence достаточно SQLite + файлового artifact store: migrations, атомарные транзакции, workspace/run/account IDs, sequence и materialized checkpoint. Это не требует vector database или распределённого event sourcing. В VS Code хранить приложение-данные вне Git по умолчанию; проектные явные правила оставлять в репозитории. Перед миграцией localStorage сделать экспорт/резервную копию; ошибки записи показывать, а не объявлять память сохранённой.

Минимальная memory record: `id, kind, accountId, workspaceId, text, sourceRefs, createdAt, verifiedAt, resourceVersion, status, sensitivity`. Для общих пользовательских предпочтений workspaceId может отсутствовать; для проектного факта он обязателен. При подключении командного backend добавить organization и серверную авторизацию, не полагаться на фильтр UI.

Не все записи должны иметь TTL: решение архитектуры и одноразовый статус сборки живут по-разному. Изменение хеша файла делает связанное утверждение требующим перепроверки. Явное пользовательское предпочтение имеет иной статус, чем предположение модели. Пользователь может просмотреть, исправить, удалить и запретить использование записи.

Автоматически сохранять подтверждённые результаты текущего run. Переносить их в долговременную память только по понятной политике: явное «запомни» или подтверждение кандидата. Не сохранять сырые рассуждения, секреты и случайные фрагменты tool output как устойчивые знания. Удаление учитывает производные summaries/индексы и явно оговорённый срок хранения журналов.

### Retrieval

Использовать уже существующий text/hybrid retrieval VS Code, а не строить новый с нуля. Начальный приоритет: точный путь/символ → lexical search → repo map/recent files → semantic retrieval при недостаточности результатов. Исключать generated/vendor/secrets по настройкам и уважать scope workspace.

Ключ индекса включает workspace, версию файла и параметры chunker; embedding entries дополнительно включают модель, размерность и версию. Устаревшие результаты маркируются и перечитываются перед изменением файла. В модели остаются источник, диапазон и признак неполноты.

Embedding/index jobs — фоновые и уступают интерактивной генерации. На текущем однослотовом runtime нельзя ради каждого поиска выгружать основную VLM и загружать embedder. Сначала lexical path; отдельная небольшая CPU embedding-модель только при измеренной пользе и допустимой памяти.

## 9. KV и физическая память

Первый шаг — prefix reuse в одном inference slot. llama.cpp уже описывает сравнение токенов запроса с прежним prompt и вычисление только отличающегося suffix; см. [закреплённую документацию llama.cpp](https://github.com/ggml-org/llama.cpp/blob/91c631b21d6e5d09e9c6659efdf6baeef5a44ddb/tools/server/README.md). Это возможность backend, а не уже реализованная возможность нашего Go engine.

- Идентичность cache: модель/GGUF, template, context и KV profile, adapter/LoRA, projector/media preprocessing; reuse только при совпадении реальных tokens/media sequence.
- `sessionId` — hint affinity, но не доказательство идентичности prompt и не механизм авторизации. Account/workspace isolation обязательны.
- Начать с текущего префикса в памяти, без неограниченного сохранения KV всех чатов на диск. Cache miss всегда корректен.
- Стабильные правила и schemas сериализовать детерминированно. Меняющиеся state/дата/заметки не должны без необходимости менять начало prompt.
- Изменение списка tools в Jinja template может менять весь префикс. Discovery экономит контекст, но на локальном backend иногда теряет cache hit: держать выбранный набор стабильным на короткий этап и измерять итог, а не постоянно пересортировывать его.
- После cancel, failure, compaction, смены модели или vision inputs корректно инвалидировать/обрезать cache. Для SWA/recurrent архитектур не предполагать произвольный откат KV без соответствующего backend support.
- KV ускоряет prefill, не устраняет стоимость генерации новых reasoning/output tokens. После его внедрения повторно измерить bottleneck.

Runtime должен быть единственным владельцем memory admission: weights + KV + projector + compute buffers + запас ОС/других процессов. Клиент получает requested/effective profile и причину адаптации. Увеличивать context ступенчато, с hysteresis и на границах run, не перезагружать модель при каждом росте истории.

Режим «Авто» сохраняется вместе с advanced override. Явные `num_ctx`, KV quant и GPU settings не менять молча; если профиль невозможен, показывать варианты. Не лечить переполнение включением overcommit по умолчанию.

## 10. Инструменты и плагины

Разделить четыре сущности: plugin package, запущенный MCP server, разрешённый набор tools, schemas, показанные модели. Установка plugin не должна означать отправку всех schemas в каждый запрос или выдачу всех разрешений.

Начальный shortlist — примерно 6–10 простых инструментов для задачи, настраиваемый по eval модели. Для кодовой задачи достаточно поиска, чтения диапазонов, patch, diff, команды и discovery; не показывать десяток синонимов записи файла. Для рабочего SaaS — несколько domain tools вместо универсального SQL/shell с широкими правами.

Host сначала выбирает известные инструменты по явному намерению, активному skill и предыдущему шагу. Для остальных доступен bounded `tool_search`: короткие описания и только разрешённые результаты. После выбора материализовать реальную native schema на следующем шаге. Универсальный `tool_call(name, arbitrary_json)` оставить совместимым fallback, но не основным интерфейсом слабой модели: он хуже ограничивается schema.

Discovery — не всегда выигрыш: дополнительный LLM round может стоить дороже небольшого каталога. Этот trade-off прямо описан в [advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use). В наших eval сравнивать fixed shortlist, host selection и model-driven search, а не переносить чужой порог количества tools.

Tool result contract: status/error code, краткое резюме, ограниченные structured data, artifact reference, cursor, source version, признак truncation. Полные логи остаются доступными через `artifact.read/search`, ошибки сборки выбираются по смыслу плюс tail, а не только первые N символов. Изображение остаётся image block, а не строкой JSON с base64.

JSON Schema проверяется host до выполнения, независимо от native grammar. Grammar ограничивает форму ответа, но не даёт разрешения и не проверяет бизнес-смысл аргументов. Валидация включает root object, required, types, enum, bounds; неизвестный инструмент не исполняется. Ошибка аргументов возвращает конкретное поле и допускает ограниченный repair.

MCP lifecycle: manifest/version/hash, compatibility, declared scopes, secret refs, single-flight start, health, timeout, cancel, crash cleanup, lazy start и idle eviction. Переиспользовать существующие shared sessions Desktop, но registry snapshot и policy делать per run/project: переключение вкладки не должно расширять права уже работающего агента.

У стороннего MCP нельзя считать `readOnlyHint` границей безопасности: чтение может отправлять данные наружу. Host контролирует filesystem roots, network destinations и sensitive-data policy; install/update plugin требует отдельного разрешения. [MCP specification](https://modelcontextprotocol.io/specification/2025-11-25/server/tools) также считает annotations недоверенными без доверенного источника и предусматривает structured/multimodal results.

## 11. Skills: переносимые инструкции, не новый исполнитель

Skill описывает процесс и критерии результата; plugin поставляет интеграцию; tool выполняет действие. Skill не может самостоятельно повысить доступ или установить исполняемый код без обычной проверки.

Единый resolver для обоих клиентов: project → user → builtin; namespace предотвращает случайное затенение. Поддержать стандартный `SKILL.md` и `.agents/skills`, сохранить миграционную совместимость с `.orchestra/skills`; одинаковые названия не должны молча теряться из-за порядка сканирования.

По умолчанию в контексте только небольшой каталог релевантных descriptors. Явно выбранный skill активируется с полным обязательным текстом; references/scripts/assets открываются по требованию. Если обязательная инструкция не помещается, сообщить о несовместимости бюджета или предложить автору структурировать skill, а не отрезать хвост. Такой жизненный цикл соответствует [Agent Skills specification](https://agentskills.io/specification).

Для маленьких моделей подготовить компактные first-party skills с ясными входом, 3–7 шагами и проверкой результата. Не использовать универсальный длинный набор «всех правил агентности» как skill на каждую задачу. Сохранить поддержку подробных пользовательских навыков без изменения их смысла.

Активный skill связан с этапом задачи и fingerprint версии. Его завершение, замена и обязательные ограничения отражаются в checkpoint. После compaction агент должен либо иметь необходимые инструкции, либо явно перечитать их перед продолжением. Permission manifest/allowed-tools является запросом capabilities, а не самостоятельным grant.

## 12. VLM как основной сценарий

Начать с end-to-end контракта `MessagePart = Text | ImageRef | ResourceRef`, адаптируемого в `image_url`, Ollama `images` и формат конкретного облака. Сохранить bytes/reference от attachment до worker и изображений, возвращаемых инструментами. Если provider/model не поддерживает vision, это явная ошибка capability, не тихая замена картинки именем файла.

Artifact store хранит оригинал, hash, MIME, размеры, происхождение, права и параметры преобразований. Ограничение разрешения и quality — модель-зависимое; для UI-анализа можно дать обзор и затем нужный crop с координатами. Исходник не теряется. OCR — вспомогательный индекс текста, не замена layout/цветов/изображения.

Одинаковую картинку не дублировать без необходимости в новом контексте. Переиспользование embeddings image encoder рассматривать отдельно от KV; разрешать только при поддержке backend, совпадающих модели/projector/preprocessing и при измеренной пользе.

Для screenshot-agent: observe → scoped action → новое наблюдение → проверка изменения. Кэш старого скриншота не является доказательством текущего UI. Перед consequential действием проверять свежесть наблюдения и target. Не запускать клик по частичному tool stream.

Eval должен различать: модель действительно увидела изображение; верно извлекла деталь; правильно связала наблюдение с инструментом; достигла результата. Текстовый тест со словом «изображение» не проверяет VLM-путь.

## 13. Локальные и облачные модели

Профиль capabilities привязывается к artifact/model version, quantization, template hash, runtime/provider version и load profile. Помимо declared support хранить результаты маленьких функциональных eval: tools, tool continuation, structured output, thinking control, vision+tools. «Модель загрузилась» не означает «модель пригодна для агента».

Обычный UI: «Авто / Быстро / Тщательно», а advanced — реальный context, output budget, reasoning effort, temperature, KV и лимиты run. Reasoning controls переводит adapter. Например, [Ollama GPT-OSS принимает уровни low/medium/high, а не выключение через boolean](https://docs.ollama.com/capabilities/thinking). Не обещать `thinking=false` для любой модели.

Reasoning отображается отдельно и не используется как проверенная долговременная память. Но transport history нельзя очищать универсальным regex: некоторые протоколы требуют возврата reasoning/opaque continuation blocks в текущем tool loop. [Ollama streaming tools documentation](https://docs.ollama.com/capabilities/tool-calling) показывает возврат накопленных thinking/content/tool calls. Правило replay должно быть per provider/model; текущий turn и долговременная память — разные вещи.

Три политики маршрутизации:

- **Только локально:** ни prompts, ни embeddings, ни summaries автоматически не уходят в облако. Сетевые plugins разрешаются отдельно и показываются — локальный inference сам по себе не гарантирует отсутствие сети.
- **Локально с предложением облака:** после объективного затруднения (неподдерживаемая capability, исчерпанный repair budget, провал проверки) показать provider и конкретный набор отправляемых данных; продолжать только после разрешения.
- **Разрешённый hybrid:** заранее заданные scope, data classes, providers и денежный лимит. Маршрутизация следует этой политике, а не уверенности модели в собственном ответе.

При смене provider передавать цель, checkpoint, актуальные доказательства и разрешённые artifacts. Не переносить необработанные чужие reasoning blocks и не дублировать уже выполненные операции. Cloud planner/local executor — один из возможных режимов после eval, не обязательная архитектура каждого запроса. На одном ноутбуке несколько локальных агентов могут конкурировать за один slot и увеличивать суммарный prefill.

## 14. Как измерять результат

Главная метрика: доля корректно завершённых задач при приемлемых времени и ресурсах, а не tokens/sec или число инструментальных вызовов отдельно.

Trace каждого run: provider/model fingerprint, requested/effective context, schema/system/history/vision token costs (estimate vs actual), cold load, queue wait, prefill, decode, first reasoning/content/tool-ready, tool time, retries, compaction time, cache reused/new tokens, peak memory, stop category. Raw prompts/artifacts — только локально по настройке; ключи и секреты редактируются. Для облака отдельно стоимость и отправленные data scopes.

Оценка задержки:

```text
run_time ≈ load + queue + Σ(prefill + decode + tool_execution + recovery)
```

Это помогает не лечить медленную генерацию reasoning только KV-кэшем и не считать быстрый ошибочный ответ улучшением.

Первый benchmark corpus — 30–50 фиксированных задач из продукта:

- прямой ответ без tools; точный workspace факт; поиск + чтение нескольких файлов;
- исправление + тест; ограниченный repair; запрещённая операция;
- malformed JSON, tool_protocol_error, interrupted SSE, timeout после внешней записи;
- plugin discovery и большой результат; skill с обязательной инструкцией в конце;
- длинный run через compaction и восстановление после рестарта;
- конфликт памяти, устаревший файл, prompt injection в tool output, изоляция двух проектов;
- VLM: скриншот, два похожих изображения, мелкий текст, crop, изображение из tool result, vision+tools.

Для Ollama/runtime: один совместимый GGUF с подтверждённым SHA, одинаковые template/входные сообщения/tools, projector и preprocessing, effective context, generation/sampling settings. Фиксировать runtime versions и прогонять cold/warm отдельно. Если Ollama artifact несовместим, это отдельный compatibility test, а не «сравнение качества на одной модели». Различающиеся templates явно учитывать как отдельный фактор.

Для cloud одинаковый набор задач и permissions, но не заявление «та же модель». Для стохастических runs — несколько повторов, p50/p95 и разброс success rate. Greedy output при KV reuse не обязан совпадать побайтно на любом backend: проверять семантику, protocol и распределение качества, учитывая numerical differences.

Первые обязательные gates:

- ни один невалидный/неразрешённый вызов не исполняется в contract test suite;
- нет тихой потери изображений, tool result или причины остановки;
- prompt compiler либо помещает обязательный контекст, либо возвращает явную ошибку до inference;
- checkpoint сохраняет цель, ограничения, pending операции и evidence через compaction/restart;
- local-only eval не отправляет данные в облако;
- для искусственного неизменного префикса второй запрос действительно считает меньше prompt tokens, а cache miss корректен.

Цели снижения latency/token расхода установить после baseline. Не принимать изменение, которое ускорило шаг, но снизило success rate или увеличило unsafe actions.

## 15. Порядок внедрения

| Этап | Содержание | Критерий выхода |
| --- | --- | --- |
| A. Контракт и baseline | Общие fixtures/provider outcomes; запрет malformed args; обработка finish_reason/stream errors; минимальные traces | В обоих клиентах воспроизводятся и проходят одинаковые protocol/error сценарии |
| B. VLM + бюджет каждого шага | Multimodal messages/results; ContextCompiler; effective context; сохранение call/result групп | Реальное изображение проходит tool round-trip; длинный run не переполняет окно молча |
| C. Повторное использование | Один slot с prefix reuse; стабильный prompt; incremental content/reasoning при tools | Warm prefill измеримо меньше; cancel/model switch/cache miss не нарушают корректность |
| D. Общая память и инструменты | Durable run journal/artifacts; shortlist/discovery; единые skills; host validation/policy | Restart/compaction не теряют действия; plugin не перегружает контекст; skill не обрезается |
| E. Управляемый hybrid | Capability profiles, data policy, cloud handoff, регрессионные eval | Смена provider сохраняет scope и состояние; нет скрытой отправки данных |
| F. Масштабирование | Обоснованные несколько слотов/моделей, programmatic tools, опциональные subagents | Выигрыш на реальных задачах при неизменных safety/quality gates |

Извлекать общую библиотеку постепенно в A/B/D: contracts → reducers/context compiler → tool broker/loop. Сначала подключить один клиент за feature flag, затем второй, сохраняя provider-specific adapters. Не совмещать большую миграцию с изменением всех эвристик и памяти в одном релизе.

В существующем runtime roadmap это поддерживает фазы 2–4, а eval из фазы 6 нужен с самого начала, не только после многомодельности. Клиентские A/B/D задачи потребуют отдельных согласованных изменений в Desktop и VS Code; runtime один их не исправит.

### Рекомендуемый первый вертикальный срез

Пользователь прикладывает скриншот и просит проверить связанный локальный файл. Агент на одной локальной VLM действительно получает изображение, вызывает read/search, получает ограниченный результат, завершает ответ с проверенными ссылками. На каждом шаге видно фактическое окно и причина остановки; повреждённый вызов не исполняется. Тот же сценарий идёт через Ollama и Orchestra с одним GGUF. Это небольшой, но полноценный тест VLM, tools, контекста и provider parity — более ценный первый результат, чем ещё один общий prompt или multi-agent framework.

## 16. Что намеренно не делать сейчас

- Не увеличивать context и число retry как универсальное исправление.
- Не показывать все plugins/skills целиком «на всякий случай».
- Не включать постоянный LLM planner/critic на каждом простом шаге.
- Не заменять доказательства свободной summary модели.
- Не складывать raw reasoning и весь transcript в долговременную память.
- Не доверять skill/MCP metadata как выданным permissions.
- Не загружать дополнительную локальную модель для каждой служебной операции.
- Не переносить на маленькие локальные модели результаты eval облачных моделей без собственного измерения.
- Не обещать одинаковую производительность на всех устройствах: quality/latency профили проверяются на доступном RAM/VRAM и реальных моделях.
