# Concerns: Orchestra Runtime (измеренные проблемы)

Дата: 2026-09-06. Стенд: MacBook M4 Pro, 24 GB unified memory, macOS 26.5.2,
бинарь `bin/orchestra-runtime` (dev-bed95d8, llama.cpp 91c631b21), Metal.
Модели: tinyllama-1.1B-Q4 (2048 ctx), Qwen3.5-9B-Q4 (8192 ctx).

Все цифры ниже получены прогоном, а не чтением кода. Метод в конце файла.

---

## C1 — Control plane блокируется на мьютексе движка (КРИТИЧНО)

**Симптом.** Во время любой генерации или загрузки модели все статус-эндпоинты,
кроме `/health`, висят до её окончания.

| Проба | Во время генерации | В покое |
|---|---|---|
| `/health` | 0.0008 c | 0.0008 c |
| `/api/tags` | **9.29 c** | 0.0005 c |
| `/api/tags` (во время загрузки 5.6 GB) | **2.32 c** | 0.0005 c |
| `/api/system` | блокируется на том же мьютексе | 0.0004 c |

В subprocess-режиме (`ORCHESTRA_USE_SUBPROCESS=1`) то же измерение даёт
`/api/tags` = **0.58 c**, `/api/system` = 0.007 c: `supervisor.Remote` уже
держит статус в атомиках с TTL 1 c и ограничивает RPC-обновление таймаутом
250 мс (`internal/supervisor/remote.go:364-394`). То есть нужный паттерн в
кодовой базе уже есть — он просто не применён к `Engine`, а дефолтный режим
работы — как раз in-process.

**Причина.** `Engine.Complete` берёт `e.mu.Lock()` на всю генерацию
(`internal/engine/completion.go:158`), `CompleteStream` держит его до конца
стрима (`internal/engine/completion.go:351`), `Engine.LoadModel` — на всю
нативную загрузку (`internal/engine/context.go:266`). А статусные вызовы
`State()`, `IsLoaded()`, `LoadedModelID()`, `ModelDesc()`, `IdleTimeout()`,
`LoadedContextSize()` берут `RLock` на том же мьютексе
(`internal/engine/context.go:386-444`) и потому ждут писателя.
Через них ходят `/api/models`, `/api/tags`, `/api/ps`, `/api/system`,
`/api/status` (`internal/service/system_info.go:90,127`,
`internal/service/model_manager.go:156`).

**Почему это и есть «нестабильность».** Клиент опрашивает рантайм с жёсткими
таймаутами: `operium-orchestra-vscode/src/modelDiscovery.ts:136` —
`/api/models` c `AbortSignal.timeout(3000)`, `OrchestraPanel.ts:6014` —
`/api/status` c `timeout(2000)`. Любая реальная работа агента длиннее 3 секунд
гарантированно даёт клиенту таймаут → рантайм выглядит мёртвым ровно тогда,
когда он работает.

**Побочный эффект.** Пока обновление статуса упирается в таймаут, воркер
отдаёт устаревшее значение — поэтому `/api/system` во время загрузки успевает
показывать `ready` (см. C14). Обработчик `MethodStatus` в воркере
(`cmd/worker/main.go:162`) сам берёт тот же мьютекс движка, так что чинить надо
с обеих сторон.

**Направление фикса.** Держать статус в атомарном снимке
(`atomic.Pointer[engineStatus]`), обновляемом на переходах состояния; читатели
статуса не касаются `e.mu` вообще. Отдельно: перевести клиентские health-пробы
на `/health`.

## C2 — При `tools` стриминг полностью буферизуется (КРИТИЧНО для агентов)

Один и тот же промпт на Qwen3.5-9B:

| Запрос | TTFB | чанков |
|---|---|---|
| `stream:true` без tools | **0.0004 c** | 302 |
| `stream:true` + 1 tool | **8.03 c** | 4 |

То есть при включённых инструментах пользователь не видит ничего до конца
генерации. Для агентного рантайма, где `tools` есть в каждом запросе, это
означает «стриминга нет никогда»: на 20B-модели это 30–60 секунд пустого
экрана на каждый шаг. Ollama и LM Studio стримят текстовые дельты и буферизуют
только сам tool-call.

Код: `internal/handler/chat.go:113` (`shouldBufferOllamaChatStream`) и
`handleOpenAIToolStream`; в `docs/ollama-compatibility.md` это зафиксировано
как осознанное ограничение («buffered SSE ... after generation completes»).

## C3 — Переполнение контекста: HTTP 500 с сырой C-ошибкой, проверка стоит после prefill (КРИТИЧНО)

Запрос ~9k токенов в модель с `n_ctx=2048`:

```
HTTP 500
{"error":{"code":"runtime_error",
  "message":"decode prompt chunk 3072-4096: llama_decode failed with code -1"}}
```

Ожидалось `400 context_length_exceeded` со структурой
(`promptTokens/contextSize/overflowTokens`) — такой тип ошибки в коде есть
(`internal/engine/errors.go:7`), но до него не доходит: guard
`if nPrompt >= nCtx` стоит **после** `prefillPrompt()`
(`internal/engine/completion.go:211-222` и `:375-388`), то есть после того, как
промпт уже начали декодировать в слишком маленький контекст. Длина в токенах
известна раньше — на `internal/engine/completion.go:554`.

Комментарий в самом коде говорит, что при `pos >= n_ctx` llama.cpp уходит в
SIGSEGV и уносит процесс. В in-process режиме (дефолт) это смерть сервера.
Для агента, который кладёт в контекст вывод инструмента, это регулярный
сценарий: длинный `git diff` или большой файл → 500 или падение.

## C4 — Нет переиспользования KV-кэша: каждый запрос — полный prefill

Один и тот же промпт (2233 токена) дважды подряд:

```
run 1: prompt_eval = 5354 ms
run 2: prompt_eval = 5130 ms
```

Переиспользования нет by design: `e.ctx.ClearKVCache()` на каждом запросе
(`internal/engine/completion.go:204`, `:368`) ради «stateless OpenAI-семантики».
Агентный цикл из 10 обращений с историей 8k токенов платит 10 полных
префиллов. llama-server (Ollama, LM Studio) держит слоты и переиспользует
общий префикс — там второй ход почти бесплатный.

Побочно: скорость префилла 2233 tok / 5.35 c ≈ **420 tok/s** на 9B Q4 на M4 Pro
выглядит низкой; требуется отдельный замер `n_ubatch`/flash-attn.

## C5 — Один слот, одна модель, никакого параллелизма

- 6 одновременных запросов исполняются строго последовательно
  (0.13 / 0.24 / 0.44 / 0.51 / 0.77 / 0.87 c).
- 80 одновременных: **65 × 200, 15 × 429** (`runtime queue full`,
  `internal/service/scheduler.go:97`, лимит `ORCHESTRA_MAX_QUEUE=64`).
- Загружена всегда ровно одна модель; обращение к другой вытесняет текущую
  (замер переключения tinyllama ↔ Qwen9B: ~1 c при горячем page cache,
  на холодной 18 GB модели это десятки секунд).

Для Operium Desktop это значит: параллельные под-агенты выстраиваются в
очередь, а fan-out больше 64 просто теряет работу с 429. Ollama по умолчанию
держит `OLLAMA_NUM_PARALLEL` слотов и до 3 загруженных моделей.

## C6 — Бюджет памяти считается от общей RAM, а не от доступной

Реальная строка лога при загрузке Qwen3.5-9B:

```
"model load plan" attempts=5 ctx_size=8192 batch_size=1024
  estimated_gb=7.10  available_gb=5.69  budget_gb=22
```

`LoadPlanner` строит бюджет как `total - 2 GB`
(`internal/service/load_planner.go:74`), поэтому загрузка идёт, хотя свободно
меньше, чем нужно. Спасает только mmap и page cache; под нагрузкой это своп и
«рантайм подвис». Metal при этом сообщает свой лимит
(`recommendedMaxWorkingSetSize = 19069 MB`), который планировщик не учитывает.

---

## C7 — mmproj грузится всегда, даже для текстовой работы

При загрузке Qwen3.5-9B автоматически подхватился
`mmproj-Qwen3.5-9B-BF16.gguf` (лог `"loading model" ... mmproj_path=...`).
BF16-проектор занимает память в каждом текстовом агентском сеансе. Нужна
ленивая загрузка при первом изображении.

---

## C8 — `<think>` протекает в `content` на `/v1`

Qwen3.5-9B, `/v1/chat/completions`, без `think`:

```json
{"role":"assistant","content":"<think>\n\n</think>\n\n4"}
```

Полей `reasoning_content` в ответе нет. Любой агент, парсящий ответ (JSON,
код, аргументы), получает мусор. На Ollama-пути разделение есть
(`applyThinkingOutput`), на OpenAI-пути в этом сценарии не сработало.

---

## C9 — Нет OpenAI `response_format` / `json_schema`

Поле в модели запроса отсутствует (`internal/model/chat.go:13-54`), запрос с
`response_format:{"type":"json_object"}` проходит как обычный текст (проверено:
модель просто продолжила промпт). Structured output есть только через
Ollama-поле `format`. Агентные фреймворки на OpenAI-совместимом клиенте
рассчитывают на `response_format`.

---

## C10 — Крэш-изоляция реализована, работает и выключена по умолчанию

Проверка `ORCHESTRA_USE_SUBPROCESS=1`: во время стрима `kill -9` воркеру →
клиент получает корректное `data: {"error":{"message":"worker process crashed"}}`,
хост поднимает новый воркер, сам перезагружает модель, следующий запрос
проходит за 185 мс. Это ровно тот уровень устойчивости, который ожидается от
Ollama.

Дополнительный аргумент за переключение дефолта: в subprocess-режиме control
plane деградирует в 16 раз мягче (0.58 c против 9.29 c, см. C1).

В дефолтном in-process режиме любой баг в llama.cpp/Metal убивает весь сервер
вместе с очередью запросов (`internal/server/server.go:54-70`). `recover()` в
стриминговой горутине (`internal/engine/completion.go:361`) от SIGSEGV в
C-потоке не спасает — это прямо написано в `cmd/server/main.go:33`.

## C11 — Логи llama.cpp смешаны с JSON-логами

В файле лога тестовой сессии **1690 строк из 1898** — сырой stderr llama.cpp
(компиляция Metal-кернелов и т.п.) вперемешку с JSON-строками slog. Парсер
логов на стороне Desktop на этом ломается, а `/api/logs` (ring buffer на 500
записей, `internal/logbuf`) видит только slog и не показывает настоящую
причину падения. Нужен `llama_log_set` → slog с маппингом уровней.

---

## C12 — Старт сервера: ~7 секунд до открытия порта

`InitBackend()` (инициализация Metal) вызывается до `ListenAndServe`
(`internal/server/server.go:66-119`); в логе `ggml_metal_library_init: loaded in
6.766 sec`. Всё это время порт не отвечает, и клиент считает, что рантайм не
поднялся. Слушатель надо открывать первым, а бэкенд инициализировать
асинхронно, отдавая `/health` со статусом `starting`.

---

## C13 — HTTP-таймауты рвут длинные агентные генерации

`WriteTimeout: 10 min`, `ReadTimeout: 5 min` (`internal/server/server.go:114`)
применяются и к SSE-стримам. Длинный агентный прогон обрывается на середине
без внятной ошибки.

---

## C14 — Прочее (не блокирующее, но в бэклог)

- Утечка при цикле load/unload: RSS 211 → 233 MB за 5 циклов (~4 MB/цикл).
  На сотнях переключений это сотни мегабайт.
- `engine_state` в `/api/system` во время загрузки успевает отдавать `ready`.
- Нет метрик (`/metrics`), нет per-request трассировки, нет серверного
  дедлайна на генерацию: запрос с большим `max_tokens` держит мьютекс движка
  сколько угодно долго.
- Раздел «Архитектура» в `README.md` описывает несуществующую структуру
  (`cmd/orchestra-runtime`, `internal/llama`, `internal/repository`).

---

## Что работает хорошо (не ломать при рефакторинге)

- Отмена запроса клиентом: обрыв SSE останавливает генерацию, следующий запрос
  обслуживается за 52 мс.
- Native tool-calling на `/v1`: корректный `tool_calls` с валидными
  аргументами, `finish_reason: "tool_calls"`.
- Автозагрузка модели по имени в запросе, hot-swap без рестарта.
- Subprocess-режим с респауном и handshake по версии/коммиту (C10).
- Адаптивный план загрузки с ретраями по OOM — идея верная, испорчена только
  расчётом бюджета (C6).
- Богатый набор sampling-параметров, включая `seed` (воспроизводимость).

---

## Метод

1. `bin/orchestra-runtime` на порту 8111 (in-process) и 8112 (subprocess).
2. Базовый чат, 6 и 80 параллельных запросов, обрыв стрима клиентом,
   переполнение контекста (~9k токенов при n_ctx 2048), переключение моделей,
   5 циклов load/unload с замером RSS, `kill -9` воркера в середине стрима.
3. Замеры латентности `curl -w '%{time_total} %{time_starttransfer}'`,
   тайминги из поля `timings` ответа, RSS через `ps -o rss=`.
4. Пробы control plane (`/health`, `/api/tags`, `/api/system`, `/api/ps`)
   параллельно с генерацией и с загрузкой модели.
